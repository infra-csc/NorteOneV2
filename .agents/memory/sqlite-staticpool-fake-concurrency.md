---
name: SQLite StaticPool tests can fake real-thread concurrency bugs
description: Real OS-thread tests against a SQLAlchemy StaticPool SQLite engine can produce false-positive "inconsistent state" failures that are pure test-harness artifacts, not application bugs. Read before writing or debugging a flaky concurrency test.
---

A common pattern for route-level unit tests is an in-memory SQLite engine created with `poolclass=StaticPool` so multiple `sessionmaker()` sessions share one DB across the test. That works fine for sequential/mocked scenarios, but it silently breaks the moment a test spins up **real OS threads** that race real `db.commit()` calls against it, for two compounding reasons:

1. **`with_for_update()` (or any `SELECT ... FOR UPDATE`) is a no-op under SQLite.** A route that relies on it for pessimistic locking gets zero real isolation in the test, even though it works correctly against Postgres in production.
2. **StaticPool hands every session the exact same underlying DBAPI connection, and SQLite allows only one active transaction per connection.** Two sessions are not two independent transactions — they are two callers sharing one. A `db.commit()` on thread A can durably flush thread B's still-pending, not-yet-committed rows (because there's only one transaction to commit), and the interleaving of individual INSERT statements between threads (via GIL scheduling) is not fixed — one run can commit a clean "all of A, none of B", another a partial mix of both.

**Symptom:** a test asserting per-thread invariants ("this call's own rows are exactly right", "status X implies code-row-count Y for the same solicitação") flakes intermittently — sometimes a thread that raised an exception still shows fully-committed rows for its half; sometimes a clean multiple-of-N invariant fails with an odd total. Rerunning the exact same test 5-10 times is often needed to even notice the flake.

**How to tell it's this, not a real bug:** re-check the route's actual write path — if the record update and all related child-row inserts happen inside a *single* `db.commit()` call with no intervening commit, the "half-saved" state is impossible against a real per-connection database. If a deterministic, single-threaded test (mocking the specific commit-time collision instead of racing real threads) reliably proves the same invariant every time, that's strong confirmation the flaky real-thread version is a harness artifact, not app logic.

**How to apply:** for routes whose only concurrency guard is DB-level locking (`with_for_update()`, unique index at commit time) with no in-process lock, don't write a real-multi-OS-thread test against StaticPool SQLite expecting to prove write atomicity — it cannot reliably do so, and a failure there is not actionable signal. Prove atomicity/rollback guarantees deterministically instead (mock the commit-time collision, single thread). Real-thread tests remain meaningful only when the code under test has its own **in-process** serialization (e.g. a `threading.Lock` keyed per resource) that prevents the two sessions from ever truly overlapping on the shared connection in the first place.

**A second, read-only manifestation:** a brand-new test file with no writes/threads of its own (plain `is_user_admin`/`user_has_permission`-style boolean checks, ORM relationship reads only) can still flake — but only when run as part of the *full* `pytest tests/` suite, never alone (10/10 clean in isolation). Symptom: a permission/relationship check returns the wrong boolean on its first evaluation inside a test, then immediately re-evaluating the exact same sub-calls on the exact same object returns the correct value — a one-shot self-correcting misread, always in the same one or two tests, at a roughly-consistent ~30-50% rate. Root cause not fully isolated (suspect global SQLAlchemy mapper/relationship machinery interacting with dozens of independent per-file SQLite engines, possibly compounded by leftover real threads from other test files sharing the process) — and it is **not** fixed by switching fixtures from module-scope to function-scope (tried and measured: identical failure rate before/after).

**Don't chase the exact mechanism — verify against real Postgres instead.** Once raw SQL / direct ORM reads inside the failing test confirm the SQLite data itself is correct (rules out a fixture bug), the fastest conclusive path is a disposable script run with real app imports against the actual dev database (`SessionLocal()` from `app.core.database`, not the test engine): create clearly-marked temp rows (unique email/marker prefix), call the real route function directly in a loop (30-40 iterations calling `db.expire_all()` between them to force fresh relationship loads), assert, then delete everything created in a `finally`. Note `app/models/__init__.py` does not import every model module (e.g. `app.models.projecao` for `AreaProjecao`/`AreaProjecaoUsuario` must be imported explicitly) — mirror whatever explicit imports the test file already uses. Clean Postgres runs (e.g. 40/40) across many iterations are strong, fast evidence the SQLite-suite flakiness is a harness artifact, not a real bug — far cheaper than instrumenting and re-running the SQLite suite dozens of times to pin down the internal SQLAlchemy trigger.
